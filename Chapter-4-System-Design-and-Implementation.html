CHAPTER FOUR: SYSTEM DESIGN AND IMPLEMENTATION

4.1 Objective of the New System

The new system, named Praxis, is a web based student union electronic voting platform created to replace the manual, paper based conduct of tertiary institution elections. The central aim is to deliver a secure and verifiable channel through which eligible students register, authenticate, review candidate manifestos, and cast their ballots within a controlled time window.

The specific objectives that guided the design are stated below:

  • To automate voter registration and institutional email verification so that only genuine students gain voting access.
  • To separate the content of a ballot from the identity of the voter, thereby guaranteeing ballot secrecy while still preventing repeat voting.
  • To compute results directly from an immutable vote ledger, removing human counting errors and shortening the interval between poll closure and result release.
  • To divide administrative authority into two tiers so that no single officer can unilaterally activate an election or publish an outcome.
  • To maintain a permanent audit record of every sensitive operation for accountability and dispute resolution.

4.4 Database Specifications

Persistent storage is handled by a relational SQLite database accessed through the Prisma object relational mapper. The schema is normalised to reduce redundancy, and a deliberate design decision keeps the cast ballot in a separate table from the voter record so that no query can link a person to a selection. The principal tables are specified below.

4.4.4 Vote and VoterRecord Tables

These two tables enforce ballot secrecy. The Vote table holds anonymous selections, while the VoterRecord table only confirms that a person participated. A composite unique constraint on the VoterRecord prevents any student from voting twice for the same seat.

Vote.castAtDateTimeTime the ballot was recorded.

VoterRecord.userIdString (FK)Participating student.

4.9 Program Documentation and Implementation

The application follows a client and server architecture. The browser client is a single page application built with the React library, while the server exposes a set of protected endpoints under a REST interface. Communication occurs over HTTP using JSON payloads, and every privileged request carries a signed token that the server validates before granting access.

On the server, an incoming request first passes through authentication middleware, then through role middleware that confirms the caller holds the required tier. The request then reaches its controller, which performs the operation through the data access layer and returns a structured response. On the client, each screen fetches its data on load and renders progressive feedback, so the user is never left uncertain about the state of an action. The build was verified after each feature by compiling the client bundle and starting both processes locally.

4.10 Language Justification

JavaScript was adopted across the entire stack. This single language choice removes the friction of switching between two syntaxes and allows shared validation logic between the client and the server.

TechnologyReason for Selection
ReactComponent based rendering keeps the interface responsive and encourages reuse of visual elements.
Node.js with ExpressLightweight and event driven, well suited to handling many concurrent voting requests.
Prisma with SQLiteA typed data layer that guards against malformed queries and simplifies schema evolution.
JSON Web TokensStateless session handling that scales without server side session storage.

4.13 User Manual

4.13.1 Guide for Students

  1. Open the platform and choose the option to create an account.
  2. Complete the form with accurate personal and academic details, then submit.
  3. Open the verification link sent to the supplied email address.
  4. Sign in and review the dashboard for elections that are open.
  5. Open an election, read the manifestos, and choose a preferred candidate for each seat.
  6. Submit the ballot and save the receipt returned by the system.
  7. Once results are released, revisit the election to view the outcome.

4.13.2 Guide for Administrators

  1. Sign in with an officer or super administrator account.
  2. Open the admin panel and create a new election with its positions and schedule.
  3. Register the aspirants for each seat through candidate management.
  4. Publish any relevant notices from the announcements area.
  5. Where a super administrator is signed in, activate the election so that voting begins.
  6. After closure, publish the results and, if a dispute arises, trigger a recount.
  7. Provision additional officer accounts from the user management area as needed.
